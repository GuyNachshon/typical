\section{Introduction}
\label{sec:intro}

Many language-model calls in production software ask for a decision: which of forty queues a ticket
belongs in, whether a transaction is fraud, how severe an alert is, which tool an agent should call
next. The caller needs a probability for each option it defines at request time, and it needs to know
when none of them fit. Today that distribution is recovered from text, by generating an answer symbol or
a JSON object, constraining decoding, or comparing candidate log-probabilities. All of these pay for
decoding and parsing, and all inherit the generative interface's sensitivity to how the answer is
written \citep{zheng2024selectionbias,pezeshkpour2024optionorder,wang2024firsttoken}.

When a causal language model reads a question followed by a list of options, the winning option is
already decodable from its hidden states before the model writes an answer symbol \citep{wong2026models}.
Typical turns that internal decision into the interface. A call maps
\[
  (\text{state},\ \text{typed question},\ \text{candidates}) \;\longmapsto\;
  \big(P(\cand{1}),\dots,P(\cand{\numcands}),\ \pnull\big)
\]
with nothing generated or parsed. The state (a ticket, a policy, an agent trace) is encoded once into a
key-value cache. Each question is a short causal suffix holding the question and its candidates, and a
head at 71\% of the backbone's depth scores the decision state against each candidate's contextual
hidden state (\Cref{fig:architecture}). The output type is a contract on the distribution: categorical
\emph{Choice}, ordinal \emph{Score}, a Bernoulli yes/no decision we call \emph{Noul}, and an abstention
probability $\pnull$ computed by a gate outside the candidate softmax.

Reading the decision out turned out to be the easy part. The hard part is making it depend on the right
inputs. A decision model can reach high accuracy while answering from which options usually go
together instead of from the question, from the hypothesis instead of the evidence, or from the state
instead of the rubric. It can also shift when the labels are reordered, when more options are offered,
or when the same content is laid out differently. Accuracy shows none of this, because a model that
leans on the wrong input is often right anyway.

We therefore built Typical around tests of what its decisions depend on. For each input that should
decide the answer we use a control that removes it, and for each factor that should not we use a
perturbation that varies it (\Cref{sec:tests}). \Cref{tab:dependence} lists what each test found in a
naive design and what Typical's design does instead. Six design choices trace to its rows: reading candidates inside the forward pass, the 71\% tap,
counterfactual rubric training, evidence-first long documents, the Bernoulli head and the abstention
gate. \Cref{sec:scale} covers probability quality and cost.

The resulting models are fast. A decision takes 45\,ms at 1.7B and 60\,ms at 14B in a research harness,
because the cached state and a short suffix dominate its cost, and the 14B model reaches .931 on the
JevBench standard tier (\Cref{sec:scale}).

\textbf{Contributions.}
\begin{enumerate}
  \item A direct decision interface for pretrained causal language models, with typed outputs and a
  factored abstention gate, that returns distributions over runtime candidates without generating text
  (\Cref{sec:method}).
  \item A protocol for testing what a decision model depends on, built on $\dq$ and render-crossed
  evaluation, which applies to any architecture that scores candidates (\Cref{sec:tests}).
  \item Design and training choices each tied to a failure that protocol exposed
  (\Cref{sec:depends,sec:invariant}).
  \item Open models, \texttt{typical-small} (1.7B) and \texttt{typical-medium} (4B), with an
  inference package (\texttt{pip install typical-ai}).
\end{enumerate}
