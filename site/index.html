JevBench disclosure. JevBench numbers are a public-subset run against fstandhartinger/jevbench v1.2.1 (72 standard / 48 easy / 111 hard public ids), not a submitted or ranked leaderboard entry (the leaderboard requires ≥95% coverage including 146 non-public judge items). Probabilities are the head's softmax conditioned on non-∅ (mean p_null ≈ .03). Latency is in-process on one H100, one decision at a time, model load excluded. Option order is the harness's label order; a reversed-order control on a related checkpoint moved standard accuracy ±4 points, larger than the differences between our own checkpoints. Chance/majority baselines are .311 standard / .284 easy / .336 hard (n = 72 standard, SE ≈ .058) — the hard tier of both released models is within 1 SE of chance.

Three question types, one head.

Choice

Pick one candidate from a set you define at runtime. Returns a probability for every option and for ∅.

Noul

A yes/no read on the same state. The only query type whose answer is exactly order-invariant.

Score

An ordered level, 0 through N, plus the expected level under the candidates.

from typical import Typical

m = Typical.from_pretrained("OzLabs/typical-small")
m.choice(state, "What does the customer want?", ["refund", "replacement", "repair"])
m.noul(state, "Is the order still under warranty?")
m.score(state, "How urgent is this ticket?", ["0", "1", "2", "3"])

Typical is an open family of small decision models. Give it a text state and a typed question (Choice over candidates you define at runtime, Noul for yes/no, Score for ordered levels) and it returns a probability for every candidate plus an explicit ∅ in one forward pass: no generation, no parsing.

It is not an LLM replacement or a knowledge model. It decides from the text you give it (≤1k tokens); it does not plan, compute, or reason over long documents, and on hard multi-step workflow judgments it is still at chance. Weights (1.7B, 4B) and inference code are open on Hugging Face.

Architecture and data →

Real games, real transcripts, one forward pass per decision.

Every demo runs the public inference/typical package, the same code behind the numbers above. Live mode calls a local model server and shows its own measured latency and device; static mode replays recorded outputs.

Works

Snake

A 10×10 board on canvas. Each tick the board is rendered as the situations that apply, pre-computed as agent-subject sentences (“the snake must move right to close the larger gap to the food”, “the snake can also move up to close the smaller gap”, “moving down hits the wall”), and the model picks one of the safe moves; the candidate set is the only guardrail. Following the sentences literally is a greedy policy that eats about 28 food per 300 ticks; the model matched it on 61/62 scripted boards (chance .48) and on 216/217 ticks of the recorded run, eating 24 food before greedy trapped it at length 27. It does not plan, and spelling the same rules out in the question made it worse (.82–.95, p_null .9).

Works

Drive

A Three.js toy road. Each tick the road is rendered as the situations that apply (“the traffic light 40 m ahead is red”, “the car is closing on a slower vehicle 17 m ahead”), seven one-condition rules are in the prompt in precedence order, and the model picks one manoeuvre from the legal set (a lane change is only offered into a clear lane). It matched the rule list on 70/70 scripted situations (chance .16; .16 for random-among-legal; .16 with no rules) and on every tick of the recorded run: 18/18 red lights, 3 lane changes, exit taken. It cannot take a rule with an “or” in it, and it reads sentence order.

Works

Doom

Chocolate Doom, the 1993 shareware, running in WebAssembly. Each tick the model reads the situations that apply, pre-computed as agent-subject sentences (“the player is badly hurt”, “the player has a zombieman in the crosshair, 6 cells ahead”, “the player must turn left to face the imp”) and picks retreat, shoot, turn left, turn right or explore from five one-condition rules; the engine only presses the key (a closed-loop turn by the enemy’s bearing) and walks a scripted route from the E1M1 spawn to the first zombiemen. It matched the rule list 48/48 in the probe (chance .20; .73 with no rules) and 200/200 in the recorded E1M1 run: 3 turns, 64 shots, 4 kills, health 86. The v3 form “the enemy is 5 cells to the left” never fired a turn (0/12); the rewrite to “the player must turn left to face the enemy” did. Raw health numbers had to go: “41 health” with an enemy in the crosshair read as danger (retreat .56 over shoot).

One document, twenty questions

A short handbook is read once into the KV cache, then twenty typed questions (12 yes/no, 5 choice, 3 score) are answered from that cached state in one call, timed against twenty one-at-a-time calls and marked against a hand label.

Works

Rules are the program

Five fixed facts about a loan applicant and four rules with a stated precedence. Reorder the rules and the model re-decides live on the same facts; a second panel runs six applicants under both orders and flags each flip.

Works

Ads

Forty short observations, each scored three ways in one call: is it an ad, which of 20 brands, which of 8 categories. The brand and category cues are written into the question, so the rules are the program; the tally compares every answer with a hand label.

Fails

Compaction

A 24-call coding-tool transcript, each call scored with a yes/no relevance question. P(keep) never crosses .5 on this pool, so there is no usable keep/drop threshold; the ranking by P(keep) is shown instead, with its AUROC against hand labels.

What does not work

  • Object-location sentences. Doom’s “the enemy is 5 cells to the left” never fired a turn (0 of 12); the model aims only once the state says “the player must turn left to face the enemy”. Numbers it must compare itself (“41 health”) leak into the decision: with them, an enemy in the crosshair at mid health read as retreat. Snake and Doom both need the engine to pre-compute the comparison.
  • Rules with "or" in them, negated conditions, or more than four rules before the default. Drive's 70/70 holds only with the state sentences in a fixed order; shuffled, it drops to .89–.93.
  • Compaction: P(keep) never crosses .5, so there is no usable keep/drop threshold, only a ranking.
  • Level-7 composition (temporal, units, expected value, trade-off): at chance on every checkpoint.
  • Long documents: states above ~1k tokens. The cause is a truncation bug in the training data; a fix is in training.

What this isn't.

Typical works from short states and literal rules over bounded candidate sets: no long documents, no vision, no arithmetic. The JevBench hard tier sits at chance and is over-confident there. Choice is order-robust, not order-invariant; reordering candidates can shift a probability by a few points.

Get started.

The public inference package ships inside the model repos on Hugging Face. Download the inference/ folder, install its requirements, then six lines of Python. state is a string or a dict; candidates are whatever you pass.

pip install huggingface_hub
hf download OzLabs/typical-small --include "inference/*" --local-dir typical
pip install -r typical/inference/requirements.txt
from typical import Typical

m = Typical.from_pretrained("OzLabs/typical-small")
m.choice(state, "What does the customer want?", ["refund", "replacement", "repair"])
m.noul(state, "Is the order still under warranty?")
m.score(state, "How urgent is this ticket?", ["0", "1", "2", "3"])
