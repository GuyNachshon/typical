Generation is the wrong interface for a decision.

A language model can tell you what it thinks. Typical hands your program a distribution over the actions it can actually take, and the odds that none of them are right. No token is ever decoded. The answer is a head on the hidden state, so there is nothing to parse, constrain or retry.

Your program keeps its logic. It gets a new kind of condition.

The questions, the options and the scale all arrive with the call — none of it is trained in. Take the winning option out of the answer space and its weight lands on the ∅ the model keeps for “none of these” — far enough that a different line of the program runs.

The second question is nearly free.

Reading the state is the work, and it happens once. A decision on a fresh state takes 45 ms; every further question against that same state adds 2.7. Thirty‑two questions on one ticket come to 129 ms — four milliseconds a decision.

Three tasks, each with the number you would get by guessing beside the number the model gets — and then the same benchmark run against general‑purpose models of every size, prompted the ordinary way.

Purpose‑built decision models from other groups score higher than this on JevBench — up to .986 standard, some of them on typical‑medium’s own base checkpoint. Our report attributes that to their rendering and method and is replicating it as a probe; until that probe lands, the gap stands as measured. JevBench figures here are a public‑subset run (72 standard / 48 easy / 111 hard public ids), not a ranked leaderboard entry, and chance is 31.1% standard. Where it works, and where it does not.

Bounded decisions over text you already have. Anything that needs several steps of reasoning, or a document longer than the state window, is outside what these two models do today.

Good fit

  • Routing and triage
  • Classification over labels you define
  • Policy and eligibility checks
  • Extraction with a closed answer set
  • Scoring on a scale you define
  • Tool choice and next action

Not yet

  • Documents past the state window
  • Serial arithmetic
  • Temporal composition
  • Multi-step planning
  • Vision, or any raw perception

Each of these has a measured failure behind it, including the ones that surprised us: object-location phrasing, rules with an “or” in them, a compaction threshold that never crosses .5, and a truncation bug that taught confident answers without evidence.

One document, twenty questions

A short handbook is read once into the KV cache, then twenty typed questions (12 yes/no, 5 choice, 3 score) are answered from that cached state in one call, timed against twenty one-at-a-time calls and marked against a hand label.

Three commands and you are running it locally.

Open weights and inference code today. The full training recipe is documented; training code comes next. Download the inference/ folder from the model repo, install its requirements, and call it. state is a string or a dict; the options are whatever you pass, per call, with no retraining.
