01 — What it is

One pass over the text. Your candidates. A probability for each, and ∅ when none of them apply.

Typical is an open family of decision models built on Qwen3 (1.7B and 4B). It does not write. It reads a state once and answers typed questions from the cached state: a Choice over candidates you define at runtime, a yes or no, an ordered level. Ask it four questions about the same ticket and it reads the ticket once.

02 — Results

Two sizes, one recipe, and a frozen backbone beside every number.

Trained and frozen backbones on the same 231 public JevBench items. Training helps the standard tier at 1.7B (+17 points) far more than at 4B (+3); on the hard tier the frozen 4B is ahead. The hard tier is at chance and over-confident for both models.

Those JevBench figures come from a public-subset run (72 standard / 48 easy / 111 hard ids), not a ranked leaderboard entry; chance is 31.1% standard, and both models’ hard tier sits within one standard error of it. The full disclosure is under the table.

03 — How it works

Three question types, one head, one cached state.

A frozen Qwen3 trunk cut at about 71% depth, LoRA on the top eight layers, and a small contextual readout with a separate abstain head. The state is read once; every question is a short suffix over that cache. Nothing is generated.

Choice

Pick one of K candidates you define at runtime. A probability for each, and for ∅.

Yes / no

A Bernoulli head on the same cached state. The only query type whose answer is exactly order-invariant.

Score

An ordered level, 0 through N, with the expected level under the candidates.

from typical import Typical

m = Typical.from_pretrained("OzLabs/typical-small")
m.choice(state, "What does the customer want?", ["refund", "replacement", "repair"])
m.noul(state, "Is the order still under warranty?")
m.score(state, "How urgent is this ticket?", ["0", "1", "2", "3"])

It is not an LLM replacement or a knowledge model. It decides from the text you give it (≤ 1k tokens); it does not plan, compute, or reason over long documents, and on hard multi-step workflow judgments it is still at chance.

05 — What does not work

Five things it gets wrong, and why.

  • Object-location sentences. Doom’s “the enemy is 5 cells to the left” never fired a turn (0 of 12); the model aims only once the state says “the player must turn left to face the enemy”. Numbers it must compare itself (“41 health”) leak into the decision: with them, an enemy in the crosshair at mid health read as retreat. Snake and Doom both need the engine to pre-compute the comparison.
  • Rules with "or" in them, negated conditions, or more than four rules before the default. Drive's 70/70 holds only with the state sentences in a fixed order; shuffled, it drops to 89–93%.
  • Compaction: P(keep) never crosses .5, so there is no usable keep/drop threshold, only a ranking.
  • Level-7 composition (temporal, units, expected value, trade-off): at chance on every checkpoint.
  • Long documents: states above ~1k tokens. The cause is a truncation bug in the training data; a fix is in training.

06 — Get started

Three commands and you are running it locally.

The public inference package ships inside the model repos on Hugging Face. Download the inference/ folder, install its requirements, and call it. state is a string or a dict; candidates are whatever you pass, per call, with no retraining.

pip install huggingface_hub
hf download OzLabs/typical-small --include "inference/*" --local-dir typical
pip install -r typical/inference/requirements.txt

The three calls themselves are the six lines shown above under How it works: choice, noul, score, each taking the same state.
